## Scope

Review the compact width-256 OOP-QCLA commutation-aware scheduler, exact
macro-entry support aggregation, live-value accounting, and fail-closed
measurement-cleanup decision. This is a logical structural result only.

## Claims requiring review

1. The linear streaming recurrence is equivalent to the complete dependency
   relation at width 256; the all-pair scan covers 754,606 pairs without
   serializing a quadratic table.
2. The unitary construction has exact model-relative macro-depth 15 and thirty
   two-phase candidate levels, witnessed by a fifteen-event critical path.
3. Common-frame macro-entry support is recomputed exactly for all 7,374 PPMs;
   possible-union and contact values are not described as simultaneous/native
   geometry.
4. Each of 240 local cleanup identities is lifecycle-valid, but every cleanup
   has a branch-specific `X(p)Z(q)` presented-observable witness and therefore
   is rejected by the current Z-only/X-only PPM family. The reported fallback
   removes zero CCXs and does not quote a raw-removal depth.
5. Native cycles, runtime, physical qubits, and failure probability remain
   null.

## Findings

Every item on the reviewer checklist was independently verified from scratch,
using scripts that import neither the new scheduler
(`width256_commutation_aware_qcla.py`) nor its shipped replay module -- only
the already-reviewed `build_oop_qcla_trace(256)`.

1. **Streaming recurrence vs. full pair oracle (checklist items 1-2).** Wrote
   an independent O(n^2) script implementing the pairwise rule directly
   (edge iff noncommuting target/control overlap, or a source CNOT layer lies
   strictly between the two source layers) and a from-scratch longest-path
   DP over all 1,229 real CCX events. Result, computed in 1.2 seconds:
   `n=1229` (matches), `C(n,2)=754,606` (matches), `dependency_pairs=251,125`,
   `admitted_pairs=503,481`, `noncommuting_pairs=3,249`, `macro_depth=15`, and
   macro-layer sizes `[255, 253, 126, 64, 34, 23, 20, 28, 40, 61, 66, 72, 53,
   70, 64]` (sum 1,229) -- an **exact match, to every integer**, of the
   generated `pair_oracle` and `macro_layer_event_counts` fields, and of the
   headline reduction from the source-aligned 17-macro/34-level baseline to
   the selected 15-macro/30-level unitary result. This independently
   confirms both that the full-oracle scan (embedded in the reviewed code as
   a self-check, `_oracle_summary`/`_oracle_nodes_and_summary`, which already
   raises if the streaming shortcut disagrees) computes the claimed numbers,
   and that a from-scratch implementation of the *same abstract rule* gets
   the same answer -- i.e. the rule itself, not just its two in-repo
   encodings, produces this result.
   I also verified the streaming recurrence's soundness argument by
   inspection: within one CNOT-barrier segment, a dependency edge exists only
   for the mirrored "earlier target = later control" / "later target =
   earlier control" cases (never for a same-segment disjoint/shared-control/
   shared-target pair, since no barrier can lie strictly between two source
   layers in the same segment by construction), so tracking, per qubit name,
   only the highest-rank earlier event that targeted it or controlled it is
   sufficient to recover the correct maximum-rank predecessor -- and across a
   segment boundary, only the single highest-rank event from all prior
   segments is needed, since *any* prior-segment event is a valid (barrier-
   forced) predecessor and only the maximum matters for the rank recurrence.
   This is the standard argument that redundant/non-minimal dependency edges
   never change longest-path length, so the shortcut is exact, not merely
   empirically lucky.
2. **Macro-entry (not sequential-within-macro) support handling (checklist
   item 3).** Read `_support_levels`: for every macro layer, phase-1/phase-2
   PPM support profiles for *all* events in the group are computed first,
   using the `columns` state exactly as it stood at the macro's entry: the
   `_column_xor` calls that fold each event's own outcome-dependent
   correction into the state happen in a *separate, later* loop, only after
   every group member's profile has already been read from the untouched
   entry frame. This matches the approved joint-injection semantics from
   `RV-20260907-001` (no event's correction may enter another event's
   incoming frame within the same macro) and is exactly the "macro-entry"
   behavior the task record says replaces an earlier flawed
   "feed one event's correction into the next" approach.
3. **Cleanup mixed-axis witness, derived independently (checklist items 4,
   6).** Verified the core operator identity by hand:
   `CZ(p,q) X_p CZ(p,q) |p,q> = (-1)^q |1-p,q> = X_p Z_q |p,q>` for all four
   basis states -- confirming `CZ(p,q) X(p) CZ(p,q) = X(p) Z(q)` exactly, the
   claimed algebraic witness. Then wrote an independent script scanning the
   real width-256 trace and confirmed, for **every one of the 240**
   `PREFIX_UNCOMPUTE` candidates (not just a sample): the value is read-only
   (only ever used as a control, never re-targeted) between its producer and
   its cleanup; its unique last quantum use before cleanup is a CCX with
   exactly two controls, one of which is the value being cleaned up; and that
   event's own direct-CCZ correction map necessarily contributes a
   `CZ(p, other_control)^{m}` term to the outgoing frame (this is the *same*
   correction-map formula already reviewed and pixel-verified in
   `RV-20260831-003`/`RV-20260907-001`, applied to that event's own two
   controls) -- so the mixed-axis contamination is a structural certainty for
   every candidate, not a coincidence found in a few cases. I independently
   recomputed the specific numbers: the earliest candidate
   (`qcla-oop:001007`) precedes exactly **236** later CCXs (matching the
   claim exactly after correctly excluding the *other* 239 removed-candidate
   gates from the "later" count, which the reviewed code does via its
   `removed_ids` filter on `suffix`). I also confirmed a upstream candidate's
   `released_target_later_ppm_use_count` is 0 for every one of the 240 rows
   in the generated artifact (checklist item 5: no later PPM ever uses a
   released target).
   I also checked this does not contradict the earlier-approved
   `T-20260906-002`/`T-20260906-003` measurement-uncompute results: those
   tasks proved only the abstract classical-channel/relative-phase identity
   and conservative *classical* outcome-frame propagation -- they never
   claimed the resulting destructive-X measurement remains a native X-only
   PPM under the retained Clifford frame, and the width-5 contract explicitly
   said the frame "must be consumed by the next dependency-model task and
   must not be treated as a free cleanup." `T-20260906-004` is the first task
   to test that specific, narrower PPM-family-compatibility question, and its
   `FALSIFIED` finding is additive, not contradictory.
4. **H/CNOT demand, live values, resource bursts, units (checklist item 6).**
   Cross-checked the generated `logical_demand`/`live_values` fields:
   `ccz_resource_state_total=1229`, `ppm_total=7374` (=6x1229, matching the
   six-PPM single-event structure already reviewed), `maximum_ccz_burst=255`

   `__post_init__` guards and the independent replay both reject any non-null
   finite-backend field).
5. **Possible-support union/contact are not promoted to geometry (checklist
   item 7).** `CandidateLevelEnvelope.__post_init__` hard-rejects
   `possible_union_is_simultaneous_weight=True`, and every generated level
   row has it `False`; the contract and generated `support_envelopes` block
   explicitly label the coordinate `logical_support_hypergraph_not_native_geometry`.
   This reuses the already-reviewed (`RV-20260903-001`/`RV-20260903-002`)
   Boolean-ANF support machinery via `direct_ccz_ppm_support_certificate`,
   invoked per-macro-layer with correct CNOT-barrier conjugation ordering (a
   macro layer is rejected if it straddles a CNOT barrier layer, and pending
   barrier conjugations are applied to the persistent `columns` state before
   each macro's profiles are computed) -- I did not re-derive the ANF engine
   itself again (already independently verified from scratch in prior
   reviews) but did verify its new per-macro invocation sequencing is correct
   by reading the code path end to end.
