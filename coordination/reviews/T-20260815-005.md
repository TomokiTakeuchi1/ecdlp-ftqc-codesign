- Reproduced all claimed commands independently: `pytest -q` -> 42 passed (50.7s); `ruff check .` -> clean; `mypy src` -> clean on 22 files; `scripts/run_adaptive_pbc_schedule_cycle.py` run twice -> byte-identical SHA-256 for all four generated files (`summary.json`, `gidney_width2_schedule.json`, `resource_state_demand.json`, `reproducibility.json`).
- Hand-verified the reported "550 -> 433 rounds (1.2702x)" synthetic-witness claim arithmetically: replacing ten separate 13-round `seed_xx` events (`10 x 13 = 130` rounds) with one 13-round `high_rate_xx_10` batch saves exactly `130 - 13 = 117` rounds, and `550 - 433 = 117` matches exactly. This confirms the high-rate batching path produces the expected serialized-time saving, not just a plausible-looking number.
- Traced the scratch-slot allocation/release logic in `schedule_adaptive_pbc_greedy` for correctness: a slot is claimed only when `owner is None` (i.e., its lifetime already fully released, which sets both `scratch_owners[slot]=None` and `scratch_available[slot]=end_round` together at release), so a new allocation can never start before its slot's true previous occupant finished. Intra-lifetime ordering (multiple operations sharing one already-active scratch carrier) is independently and correctly enforced through `carrier_available[f"scratch:{slot}"]`, which is updated after every operation touching that carrier, not only at allocation/release. I confirmed this two-mechanism split is sound rather than a gap: `scratch_available` need only answer "when is this slot next free for a *new* lifetime," which release-time updates suffice for, while `carrier_available` answers "when is *this* carrier free for its *next own* use," which is updated every time. `start_round = max(...)` over both correctly enforces the tighter of the two regardless.
- Verified why "ten distinct live scratch slots" is the right frame for the high-rate rule rather than an arbitrary extra restriction: each CNOT gadget's XX measurement (from the already-approved `T-20260815-004` lowering) is tied to exactly one scratch carrier (its own `cnot_scratch`), so requiring ten simultaneously-*active* (allocated-but-not-yet-released) distinct scratch lifetimes is the natural generalization of "ten ready, pairwise-disjoint XX measurements" to a resource-constrained schedule, and is distinct from requiring ten *concurrently executing* operations (which the single-capacity `processor_operation_zone` would forbid regardless). This is why testing with `scratch_slot_count=10` is a meaningful, separate experiment from `scratch_slot_count=1`, and why both still report zero eligible batches for the real Gidney widths -- the bottleneck is genuinely the ripple-carry adder's limited independent parallelism at these widths (critical path is 75%+ of total scheduled rounds at every tested width), not a scratch-count artifact. The `_ten_independent_cnot_trace` synthetic witness isolates exactly this distinction and confirms the batching code path itself works.
