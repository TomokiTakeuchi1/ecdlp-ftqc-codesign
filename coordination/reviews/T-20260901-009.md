## Reviewer findings

This is the first task in the direct-CCZ PPM line to touch the core compiler
and scheduler modules rather than adding a presentation layer, so the review
focused on (a) proving the OOP path is truly unaffected and (b) independently
re-deriving the new IP-specific math rather than re-running the implementer's
own scripts and trusting the output.

1. **OOP-path preservation, verified by code-structure proof, not just by
   test.** Read the full diff of `direct_ccz.py`, `direct_ccz_ppm.py`, and
   `direct_ccz_ppm_batching.py` line by line. The refactor extracts private
   shared helpers (`_lower_toffoli_to_direct_ccz_event`,
   `_lower_qcla_to_symbolic_direct_ccz_ppm`) and re-exposes the previous public
   OOP entry points as thin wrappers that call the shared helper with
   OOP-specific inputs (`lower_oop_qcla_to_direct_ccz_events`,
   `_oop_logical_lifetimes`, unchanged bodies). The only new branch inside the
   shared lowering loop (`if gate.kind in {CNOT, X}`) degenerates to the
   byte-identical old CNOT-only branch for OOP, since `FrameGate.support` is
   exactly the tuple passed at construction, so `','.join(logical_gate.support)`
   reproduces the previous hardcoded `f"CNOT({controls[0]},{target})"` string
   exactly. Beyond this structural argument, I ran the repository's own
   `test_oop_symbolic_trace_remains_byte_identical` (which freshly regenerates
   the OOP trace and diffs it against the untouched `T-20260901-006` artifact
   on disk) and independently reloaded that same reference file myself,
   confirming it still reports 23 source operations / 60 PPMs before trusting
   the diff.
2. **X-frame conjugation.** `SymbolicPauliWord.apply_gate`'s `FrameGateKind.X`
   case (`sign ^= z_component`) was NOT touched by this diff — it already
   existed and was already matrix-verified against explicit unitaries in the
   `T-20260901-006` review (confirmed by finding the existing matrix test at
   `tests/unit/test_direct_ccz_ppm.py:169`). This task is the first to actually
   exercise that code path via source passthrough, and the generic
   `_conjugate_frame_by_gate`/`_normalize_circuit` sandwich-and-cancel logic
   (unchanged, gate-kind-agnostic) is reused rather than re-implemented for X.
   The independent replay module's `_conjugate_terms_by_gate` reimplements the
   sandwich rule from scratch in a separate code path and is exercised by
   `test_ip_replay_rejects_tampered_x_passthrough`, which I reran and confirmed
   fails closed when an X instruction's logical-gate kind is corrupted.
3. **Exact-vs-bounded profile boundary (the main new piece of math).**
   Independently re-derived that `_exact_axis_options`'s per-branch axis test
   (`x AND NOT z` → X, `x AND z` → Y, `NOT x AND z` → Z, tested via
   `BooleanPolynomial.is_zero`) is mathematically identical to
   `SymbolicPauliWord.evaluate`'s per-branch `{(0,0):I,(1,0):X,(0,1):Z,(1,1):Y}`
   lookup, so replacing brute-force `2^n`-assignment enumeration with an exact
   ANF existence test cannot change the axis_options result for any profile,
   independent of variable count. Independently confirmed `minimum_weight=1` is
   a valid proved lower bound for profiles above the 16-variable enumeration
   boundary (a Clifford conjugate of a nonidentity Pauli is never the identity,
   a standard stabilizer-formalism fact), and that `maximum_weight = len(axis_options)`
   is a valid (if conservative) upper bound (the exact union of branch-possible
   support cannot be exceeded by any single branch). Confirmed via the shipped
   test suite and my own independent load of the raw JSON that exactly 7 of 120
   profiles are marked `weight_bounds_exact=False`, all with
   `minimum_weight=1` and `distinct_branch_observables=null`, and that none of
   this weakens Y/axis/commutation/causal/reaction classification, which stay
   exact ANF decisions for all 120 profiles regardless of variable count
   (unchanged functions, confirmed unmodified in the diff).
4. **Large-instance conflict-clique shortcut.** Confirmed the `len(ppm_ids) <=
   60` threshold routes OOP's 60 PPMs through the exact, byte-identical
   maximum-clique code (unchanged besides reformatting) and IP's 120 PPMs
   through a new `single_vertex_proved_lower_bound_large_instance` shortcut
   that returns `1` rather than solving a 120-vertex NP-hard clique problem.
   Verified this cannot silently weaken the `PROVED` claim: `combined_lower =
   max(causal_lower, conflict_lower)` and `upper = len(batches)` are both
   computed from the actual data (not hardcoded), and since IP's causal bound
   alone is 24 and matches the 24 constructed levels, the trivial clique bound
   is provably never the binding term. The independent batching-replay module
   was extended with its own dispatch on `conflict_clique_bound_method` that
   (a) rejects the large-instance shortcut if used below the 60-PPM threshold
   and (b) still runs the exact clique algorithm whenever that method is
   claimed, so the shortcut cannot be silently substituted for a real instance
   that needed the exact computation.
5. **Independent from-scratch verification script** (imports nothing from
   `ecdlp_ftqc.compiler`/`scheduler`/`verification`; written against the raw
   JSON in `experiments/runs/T-20260901-009/` and the untouched
   `T-20260901-006` reference file):
   - A Monte Carlo cross-check evaluated 400 randomly sampled pair relations at
     300 random Boolean outcome-assignments each (120,000 evaluation points),
     using a hand-written ANF polynomial evaluator built directly from the raw
     `anf_monomials` JSON, and found zero contradictions of any claimed
     `universally_commuting`, `universally_axis_consistent`,
     `left_has_possible_y`, or `right_has_possible_y` value.
   - An independent topological-sort + longest-path DP (built from
     `causal_order == "left_before_right"` edges in the raw pair-relation
     table, not from the reviewed `_longest_ppm_path`) reproduced the causal
     lower bound of exactly 24.
   - Hand-verified combinatorics: `C(120,2)=7140`; batch sizes
     `12,12,6,6,3×14,6,6,9,9,6,6` sum to 120 with no PPM omitted or
     duplicated; within-batch pairs `2·C(12,2)+2·C(6,2)+14·C(3,2)+2·C(6,2)+2·C(9,2)+2·C(6,2)=336`;
     cross-level pairs `7140-336=6804`.
   - Confirmed the 7 bounded profiles' `minimum_weight`, `distinct_branch_observables`,
     and the schedule's `conflict_clique_bound_method`/`conflict_clique_batch_levels`
     values directly from the raw JSON, independent of the shipped tests.
   All checks in this from-scratch script passed on the first run.
6. **Semantic correctness of the arithmetic itself.** Reran the shipped

7. **Reproducibility.** Reran `scripts/run_direct_ccz_ip_qcla_cycle.py` twice

8. **Tests, lint, types.** Reran `tests/unit/test_direct_ccz_ip_qcla.py` (12
   passed), the combined QCLA/OOP/direct-CCZ/atlas/Hub suite (178 passed),
   `ruff check src tests scripts` (clean), and `mypy --strict src

## Review disposition

**APPROVED.** The generalization of the direct-CCZ event adapter, symbolic
PPM/frame compiler, exact-ANF batching classifier, and both independent replay
modules to accept in-place QCLA is structurally sound, mathematically correct,
and leaves the already-reviewed OOP path provably unaffected. The new
exact-vs-bounded profile boundary and the large-instance conflict-clique
shortcut are both honestly labeled, do not weaken any exact compatibility
decision, and were independently re-derived and empirically cross-checked
(120,000-point Monte Carlo sweep plus an independently reimplemented causal
longest-path DP) rather than merely re-run. All claimed counts (43 source
operations, 20 events, 120 PPMs/updates, 75 dependencies, 7,140 pairs, 24
candidate levels matching the causal lower bound, 7 bounded profiles) were
independently reproduced from raw serialized data. Known limitations (width
scaling and finite-backend integration deferred to `T-20260901-010`; candidate
levels are not surgery rounds; the one-vertex clique bound is not a maximum
clique; seven profiles have only conservative weight bounds) are accurately
preserved throughout the contract, ledger, and Research Hub records.
