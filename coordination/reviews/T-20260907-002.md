## Scope

Review the common deterministic branch-maximum PPM-weight comparison for the
already-reviewed width-256 OOP 15/30 and IP 30/60 logical candidates. This
task adds a distributional logical-support overlay; it does not change either
schedule or admit a native surgery construction.

## Claims requiring review

1. For one candidate level and fixed global outcome assignment, the reported
   quantity is exactly the maximum presented logical PPM support weight among
   all PPMs in that level.
2. The packed 512-sample implementation correctly applies all source CNOT
   conjugations and the two support-changing Figure-14(a) target-column
   updates, without applying one same-macro event's correction before another
   event at the common entry.
3. OOP/IP largest p95 values are 168/188, p99 values are 198/222, and maxima
   over the 510 hashed assignments are 223/248. Both full sampled maxima are
   509 because the forced all-one boundary assignment dominates.
4. Sample statistics remain `NUMERICAL`; the separate OOP exact/IP
   may-support ceilings remain 1,003/1,006 with their prior evidence labels.
   No sampled maximum is promoted to an exhaustive maximum.
5. Every phase-two fresh-resource X level has exact unit weight, and native
   time, space, routing, service, and failure outputs remain null.

## Known limitations disclosed by implementer

- The 512 assignments are deterministic witnesses, not an outcome probability
  model, confidence sample, or exhaustive enumeration.
- The forced boundary branches are deliberately correlated extremes. Their
  maxima must not be interpreted as empirical tail frequency.
- A logical PPM support weight is not connected code support, code contact,
  routing load, surgery duration, or simultaneous physical geometry.
- The IP ceiling remains a may-support `CHECK` bound; this task does not close
  its 29 previously unresolved levels.
- H/CNOT materialization, reaction/decoder service, factory/buffer service,
  native cycles, runtime, physical qubits, and failure remain uncomputed.

## Findings

Every checklist item was independently verified from scratch, using scripts
that import neither the primary sampler
(`width256_oop_ip_branch_weight_sampling.py`, scheduler side) nor its
shipped scalar-replay counterpart -- only the already-reviewed circuit
builders, direct-CCZ compiler, and the two already-approved commutation-aware
study builders (used only for their `macro_layers` grouping, which is not
what this task is being tested on).

1. **Deterministic assignment reconstruction and forced boundaries (checklist
   item 1).** Confirmed by direct inspection of `_sample_mask` in both the
   scheduler and its replay: a SHAKE-256 digest of `f"{seed}|{token}"` is
   truncated to 512 bits, then bit 0 is forced to `0` and bit 1 is forced to
   `1` for **every** token -- this exactly and mechanically produces "branch
   0 = all outcomes zero" and "branch 1 = all outcomes one" regardless of the
   hash, with the remaining 510 bits genuinely hash-derived. Both
   implementations use the identical formula, and the shipped scalar replay
   independently recomputes `_assignment_digest` and compares it against the
   stored `support_relevant_assignment_sha256`, which the test suite
   confirms passes.
2. **Independent physics reconstruction, third implementation (checklist
   items 1-2, 5).** Wrote a **third**, deliberately different reimplementation
   of the support-propagation rule -- plain Python `dict[str, set[str]]`
   columns with set symmetric-difference for CNOT/conditional updates,
   instead of either the scheduler's 512-wide integer bit-planes or the
   verifier's per-branch integer bitsets -- and used it to compute the two
   *deterministic* boundary branches (all-zero, all-one) for both OOP and IP
   directly from first principles. My first attempt had a real bug (a wrong
   XOR-toggle condition in the row-update step); after finding and fixing it
   by comparing intermediate output, the corrected script reproduced the
   full sampled maximum **509 at OOP level 29** and **509 at IP level 31**
   exactly, matching the contract table and the generated data to the exact
   integer, together with the complete all-zero baseline (constant weight 2)
   and the full all-one growth/decay curve for every one of the 30 OOP and
   60 IP levels. This independently confirms both the CNOT source-Clifford
   conjugation rule and the "only the first two Figure-14(a) outcomes
   condition target-touching updates" rule (checklist item 3) are correctly
   implemented, using a genuinely different data structure than either
   shipped module.
3. **Quantile/statistics layer, recomputed directly from stored vectors
   (checklist item 4).** Wrote an independent script that loads the raw
   generated `branch_weight_study.json`, and for **every one of the 90
   levels** (30 OOP + 60 IP) recomputes the nearest-rank p50/p95/p99 from the
   stored 512-entry vector via `ceil(p*N/100)`, the hashed-branch maximum
   (`max(vector[2:])`), the sampled maximum, and the sampled-to-ceiling gap
   -- all matched exactly, with zero mismatches. Separately recomputed the
   "largest across all Z levels" hotspots and got, to the exact integer and
   level: OOP p50/p95/p99/hashed-max/sampled-max/ceiling/max-gap =
   `98(21)/168(25)/198(25)/223(25)/509(29)/1003(29)/494`; IP =
   `122(59)/188(31)/222(39)/248(33)/509(31)/1006(31)/622` -- an exact match
   to every number in the contract's headline table (including every tie
   the table records, e.g. OOP p50 at levels 21/23 and IP hashed-max at
   33/49/51).
4. **Evidence-label boundaries not conflated (checklist item 5).** Verified
   every sampled Z-level value is `<=` its recorded
   `support_weight_upper_bound`, and that the OOP ceiling
